# 单机测试双人效果

> 对应《Duetto Demo 制作说明》4.2「同步模式」。
> 本文回答：硬件只有一套，怎么在电脑上把双人效果跑通、调好、录下来。

---

## 核心思路：状态机是纯对象，多 new 一个就是多一个人

`EyeStateMachine` 没有任何全局状态或单例，所有动画数据都在实例里。所以：

```python
sm_a = EyeStateMachine()   # 你
sm_b = EyeStateMachine()   # 对方
```

两个实例各跑各的 `update(dt)`，就是两个"人"。屏幕和灯带只是渲染层的两份拷贝。

这不只是省钱——**它能让你在硬件到位前就把以下三件事做完**：

1. 共鸣判定的参数（窗口多宽、持续多久、冷却多长）
2. 对视彩蛋的视觉方向（哪台往哪偏）
3. 灯带左右分区在共鸣时的合并逻辑

这三件事如果等到两台硬件都齐了再调，一次只能试一个参数，而且两个人得约时间。

## 三种模式，按场景选

### 模式一：`split` —— 单人双手，最接近真实

```bash
python3 duetto_duo.py --mode split
```

| 设备 | 轻敲 | 重击 | 9 宫格 |
|---|---|---|---|
| **A（左屏）** | `F` | `空格` | `Q W E` / `A S D` / `Z X C` |
| **B（右屏）** | `K` | `回车` | `U I O` / `J K L` / `M , .` |

左手管 A，右手管 B。**两只手同时敲 = 两个人同时敲。**

这是最值得用的模式——因为"两个人"和"一个人两只手"在时序上的差别，恰恰是要调的东西：

- 两个人不可能完全同时，总会有 100–400ms 的错位
- 两只手你完全可以做到 50ms 内同步，反而测不出真实情况

所以调参时**刻意把两只手的动作错开一点**，比完全同步更接近真实数据。

### 模式二：`ai` —— 单人演示，路演用

```bash
python3 duetto_duo.py --mode ai --synergy 0.65
```

你只操作 A 机。B 机看到一个动作后，延迟 120–420ms 按 `synergy` 概率跟一手。

- `--synergy 0.9`：几乎每次都跟，共鸣频繁，演示效果炸
- `--synergy 0.4`：经常走神，共鸣稀有，显得"珍贵"

**这个模式的价值不只是演示**：它把"对方的响应延迟"和"同步概率"变成了两个可调旋钮，让你在没人的时候也能压测判定逻辑。

### 模式三：`replay` —— 排除人的因素

如果共鸣该触发却没触发，你需要知道是**判定逻辑错了**还是**你手速问题**。录一段回放，用固定输入重跑，就能排除后者：

```bash
python3 duo_bridge.py --simulate --record --out take1.json   # 先录一段
python3 duo_bridge.py --replay take1.json                    # 再用它重跑
python3 duo_bridge.py --replay take1.json --swap              # 交换 A/B
```

`--swap` 会交换 A/B 两台。**同一个录制文件，正常跑和 swap 跑，共鸣次数应该一样**——如果不一样，说明判定逻辑有单边偏置（比如总是"先动的那台"更容易触发）。这个检查我跑过了，当前实现是对称的。

## 电脑端中枢：`duo_bridge.py`

按说明 4.1/4.2 实现的串口桥接，**没有硬件也能跑**：

```bash
# 无硬件，验证全链路
python3 duo_bridge.py --simulate --record

# 有硬件
python3 duo_bridge.py --a /dev/cu.usbserial-A --b /dev/cu.usbserial-B --record

# 查串口
python3 duo_bridge.py --list
```

实现的协议与说明一致：

| 方向 | 内容 |
|---|---|
| 硬件 → PC | `I` / `T` / `L` / `R` / `U` |
| PC → 硬件 | `S1`（进入共鸣）/ `S0`（退出）/ `P_X`（对方状态） |

记录文件格式：

```json
{
  "meta": { "resonance_hits": 3, "protocol": "I/T/L/R/U @115200" },
  "events": [
    { "t_ms": 3202, "device": "A", "state": "U" },
    { "t_ms": 3610, "device": "B", "state": "U" }
  ]
}
```

## ⚠️ 一个需要改说明的地方：1.5 秒窗口太宽

说明 4.2 写的是「过去 1.5 秒内双方都出现激烈情绪」就触发共鸣。实测下来这个值有问题：

模拟跑 16 秒、窗口 1.5s，触发了 **3 次**，其中一次两边差了 **0.37 秒**。但现实里两个人听同一首歌，副歌同时嗨起来，差 0.37 秒已经算「没对上」了——一个人已经滑完了，另一个人才开始。

把窗口收到 **0.8 秒**，同样的模拟只触发 2 次，质量明显更高。

**建议**：`duo_bridge.py --window 0.8` 起步，现场根据彩排效果调。

判定逻辑本身也值得再收紧。现在是「窗口内两边都出现过 T 或 U」，更严格的做法是**双方都在同一个"高潮段"内**——但那就需要知道歌曲进度，Demo 阶段不必做。

## 对视彩蛋的方向（容易搞反）

说明里写「左机表情向右偏、右机表情向左偏」。代码里对应：

```python
# A 机在左 → 往右看；B 机在右 → 往左看
p.head_x += look_shift * 0.085   # A: +1, B: -1
p.head_tilt = look_shift * 7.0
p.smile = max(p.smile, 0.85)
```

我第一次实现时两边取了同一个方向，两台设备变成"一起看左边"，完全不像对视。这个错误在单机上很难发现，**必须两台并排看才能看出来**——所以单机双人视图的第二个价值就是这个。

---

## 建议的调参顺序

1. **先跑 `--simulate`**，确认判定逻辑和记录格式没问题（不需要任何硬件）
2. **再跑 `split` 模式**，两只手错开 200–300ms 操作，看共鸣频率是否合理
3. **调 `--window`**：从 1.5 收到 0.8，找到"该触发时触发、不该触发时不乱触发"的甜点
4. **最后接真机**：两台串口接上，用同一套 `Bridge` 逻辑，此时只是把 `SimDevice` 换成 `SerialReader`

第 4 步几乎不用改代码——`Bridge` 的数据源是注入的，模拟设备和串口读线程都是往里 `feed()`。
